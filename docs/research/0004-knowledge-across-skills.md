# Where shared knowledge lives in seven agent-skill repositories, and what a skills-only install carries

## Answer

The table gives each repository's handling of each item. The sections below cite every cell.

| Repository | Where shared knowledge lives | How skills reach it | Who owns artifact formats | What keeps copies from drifting | After a skills-only install | What setup writes into the consuming repository |
| --- | --- | --- | --- | --- | --- | --- |
| superpowers | Inside skill folders; cross-skill rules in `skills/using-superpowers/`, which a SessionStart hook injects | `superpowers:<name>`; some `../` links into sibling skills; scripts by skill-relative path | The writing skill, inline (`writing-plans`, `brainstorming`); `task-brief` script also parses plan headings | No shared text is copied; `bump-version.sh --check` compares manifest versions only; no CI workflow | No such install offered; Inferred: a copy loses the hook and `../` links | Nothing at install; skills later write `docs/superpowers/specs/`, `docs/superpowers/plans/`, `.superpowers/sdd/` |
| mattpocock/skills | In the owning skill (`domain-modeling/GLOSSARY-FORMAT.md`); repository facts in the consuming repository's `docs/agents/*.md` | "Call the Skill tool" by name; prose pointers; `chief-of-staff` uses `../<skill>/SKILL.md` | The owning skill; setup's seed templates own `docs/agents/*.md` | Written conventions; CI checks frontmatter only; seeded files refresh only on a setup re-run | Offered (skills.sh, `gemini skills install`); works only when the called skills and setup are picked | `setup-matt-pocock-skills` writes `docs/agents/*.md` and an `## Agent skills` block in `CLAUDE.md` or `AGENTS.md` |
| elephant-goldfish-model | Plugin root, outside skills: `resources/`, `agents/`, `docs/`; two skills keep own `references/` | `../../resources/…`, `${CLAUDE_PLUGIN_ROOT}/…` and `~/.gemini/…` fallback, plus inline fallback rules | `resources/document_standards/`; templates inside `egm-draft` and `egm-bootstrap` | One canonical copy, thin pointers, unit tests that every path resolves; symlinks rejected | Breaks, by its own docs; whole-plugin install only | No install step writes there; `egm-bootstrap` writes `README.md` or `EGM.md` contracts |
| gsd-core | Shared `gsd-core/` tree (workflows, references, templates) and the `gsd-tools` CLI; skill folders are generated wrappers | `@~/.claude/gsd-core/…` includes that the installer rewrites per runtime; a plugin hook symlinks the tree; CLI calls | `gsd-core/templates/`; the CLI, with `src/state-document.cts` designated owner of `STATE.md` grammar | `skills/` generated from `commands/gsd/`; `lint:generated-sync` runs `--check` generators | Not offered; Inferred: every `@` include would dangle | npm installer writes runtime folders (`.claude/gsd-core/` at local scope); `/gsd-new-project` writes `.planning/` and the instruction file |
| spec-kit | CLI source tree: `templates/`, `scripts/`, `specify_cli` | Tokens (`__SPECKIT_COMMAND_<NAME>__`, `{SCRIPT}`) rewritten at render; project files under `.specify/` | Shared core templates, layered by presets and extensions through a resolver script | One source; rendered copies hash-tracked in a manifest; parity tests across script variants | Not offered; maintainer declined `npx skills` on 2026-11-18 | `.specify/` (scripts, templates, state), rendered skills in each agent's folder, hook settings; root files only through an opt-in extension |
| OpenSpec | TypeScript CLI: `src/core/templates/workflows/*.ts` and `schemas/` | Skill name; CLI calls such as `openspec instructions`; the router skill's `references/` | The schema (`schema.yaml` plus templates), served by the CLI | Committed `skills/` is generated; a parity test diffs it in CI, skipped on docs-only PRs | Offered (`npx skills add`); instructions arrive, formats need the separate `openspec` CLI | `openspec/config.yaml` and `openspec/`; skills machine-wide by default, or `.agents/skills/` with `--scope project` |
| BMAD-METHOD | `bmad` skill's `scripts/`; per-module record skills `bmod-<module>/` (help, templates); maintainer files in `tools/` | `uv run {project-root}/_bmad/scripts/…`; "Invoke the `x` skill"; scripts scan installed records | Templates in records or the skill; `tickets.py` plus rules each skill restates; `setup.py` for config | Setup recopies scripts when the tree differs; prose copies by hand; validators check references in a flat copy | The supported install; records arrive as skills; shared scripts only after `bmad setup` | `_bmad/` (scripts, `config.toml`, module scripts, `render/`, `custom/`); output under `_bmad-output/`; an `AGENTS.md` block on approval |

- **Where they agree.** No repository lets a skill reach a hand-edited shared folder by relative path after a folder-by-folder install. Shared knowledge reaches an installed skill by one of three routes:
  - a whole-plugin install that keeps the plugin root (superpowers, elephant-goldfish-model, the gsd-core plugin);
  - a CLI that renders or serves it (spec-kit, OpenSpec, gsd-core);
  - a setup step that writes it into the consuming repository (mattpocock/skills, BMAD-METHOD, spec-kit).
- **Where they differ.** Three repositories support skills-only installs: mattpocock/skills, OpenSpec and BMAD-METHOD. Each still needs something outside the folder: the called skills, the CLI, or `bmad setup`. Format ownership splits the same way. In superpowers and mattpocock/skills one skill owns each format. In elephant-goldfish-model, gsd-core, spec-kit and OpenSpec a shared template, schema or CLI owns it.
- **Recent movement, October and November 2026.** Several repositories now copy shared files into the skill folder at install time:
  - spec-kit's `resources` copy mode shipped in v1.4.3 (2026-11-19).
  - OpenSpec's router `references/` shipped in 2.2.0 (PR merged 2026-11-24).
  - BMAD PR #3288 (open, 2026-11-28) would vendor byte-identical script copies into standalone skills.
  - elephant-goldfish-model went the other way: PR #13 (2026-10-02) removed byte-identical copies in favour of one `resources/` folder.
- **Drift checks.** Two checks compare a generated copy with its source: OpenSpec's `skillssh-parity.test.ts` and gsd-core's `gen-plugin-skills.cjs --check`. elephant-goldfish-model tests that pointers resolve. superpowers has no CI workflow.
- **Reported problems, with dates.**
  - A skill fails when a skill it calls is not installed: mattpocock/skills #475 (2026-07-08) and #1319 (2026-10-22), both open; OpenSpec #1975 (2026-09-25), closed.
  - A skill points at a file the install does not ship: BMAD #3244 (2026-11-21) and #3008 (2026-10-01); mattpocock/skills #1458 (2026-11-20); gsd-core #5654 (2026-10-24).
  - A plugin-root path does not resolve under one harness: elephant-goldfish-model #455 (2026-11-16, open); superpowers `${CLAUDE_PLUGIN_ROOT}` reports from August to October 2026.
  - A shared copy in the consuming repository is stale: BMAD #3209 (2026-11-16). Inline copies of a rule drift: mattpocock/skills #1332 (2026-10-26).
  - Installer rewrites miss some paths: spec-kit #5363 (2026-11-10); gsd-core #6747 (2026-11-27, open).
- **Strength of the evidence.** Each repository was read at one default-branch commit, and no installer was run. Skills-only behaviour for superpowers and gsd-core is inferred from file layout, not tested. The BMAD tree is the V7 preview, not release v6.12.4. Several fixes sit on `dev` branches or in open PRs. Most mechanisms above are weeks old.

## How do `obra/superpowers` and `mattpocock/skills` handle each item under Constraints?

### obra/superpowers

- The tree at the pin has no shared or template folder outside `skills/<name>/`; supporting files sit in per-skill `references/`, `scripts/` and `templates/` (tested 2026-11-28: `git ls-files` in the clone).
- `using-superpowers` holds the cross-skill rules and points at per-harness tool files ([SP skills/using-superpowers/SKILL.md](https://github.com/obra/superpowers/blob/22f0b463e7/skills/using-superpowers/SKILL.md)): "If your harness appears here, read its reference file for special instructions".
- The SessionStart hook reads that file from the plugin root and injects it ([SP hooks/session-start](https://github.com/obra/superpowers/blob/22f0b463e7/hooks/session-start)): `skill_md="${PLUGIN_ROOT}/skills/using-superpowers/SKILL.md"`.
- Cross-skill references use `superpowers:<name>` ([SP skills/writing-plans/SKILL.md](https://github.com/obra/superpowers/blob/22f0b463e7/skills/writing-plans/SKILL.md)): "REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans" (tested 2026-11-28: `grep -rnoE 'superpowers:[a-z-]+|\.\./…' skills` in the clone).
- Some files link into sibling skill folders, for example `final-review.md` to `../../requesting-code-review/code-reviewer.md` (same grep; [SP final-review.md](https://github.com/obra/superpowers/blob/22f0b463e7/skills/subagent-driven-development/references/final-review.md)).
- A skill reaches its own scripts by a path relative to its folder ([SP skills/subagent-driven-development/SKILL.md](https://github.com/obra/superpowers/blob/22f0b463e7/skills/subagent-driven-development/SKILL.md)): "`bash scripts/task-brief PLAN_FILE N` by its absolute path".
- `writing-plans` owns the plan format inline ([SP skills/writing-plans/SKILL.md](https://github.com/obra/superpowers/blob/22f0b463e7/skills/writing-plans/SKILL.md)): "**Save plans to:** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`" and "**Every plan MUST start with this header:**".
- `brainstorming` writes specs to `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` ([SP skills/brainstorming/SKILL.md](https://github.com/obra/superpowers/blob/22f0b463e7/skills/brainstorming/SKILL.md)).
- The `task-brief` script encodes its own reading of the plan format and writes to `.superpowers/sdd/<plan-basename>/` ([SP skills/subagent-driven-development/scripts/task-brief](https://github.com/obra/superpowers/blob/22f0b463e7/skills/subagent-driven-development/scripts/task-brief)): "Depth alone is not enough: plans drift from \"## Task 1\" to \"### Task 2\"."
- `bump-version.sh --check` compares only the version fields of the manifests in `.version-bump.json`; no skill file is listed ([superpowers `scripts/bump-version.sh`, 22f0b463e7](https://github.com/obra/superpowers/blob/22f0b463e7/scripts/bump-version.sh); [superpowers `.version-bump.json`, 22f0b463e7](https://github.com/obra/superpowers/blob/22f0b463e7/.version-bump.json)).
- `.github/` holds no workflow (tested 2026-11-28: `gh api --method GET "repos/obra/superpowers/contents/.github?ref=22f0b463e7"` returned `["FUNDING.yml","ISSUE_TEMPLATE","PULL_REQUEST_TEMPLATE.md"]`).
- The README lists only per-harness plugin or extension installs ([SP README.md](https://github.com/obra/superpowers/blob/22f0b463e7/README.md)): "Installation differs by harness." A grep for `npx skills` or `skills add` in `README.md` and `docs/*.md` found nothing (tested 2026-11-28).
- The porting guide requires the harness's own installer and forbids editing user files ([SP docs/porting-to-a-new-harness.md](https://github.com/obra/superpowers/blob/22f0b463e7/docs/porting-to-a-new-harness.md)): "Everything ships through the harness's own install mechanism." and "Never edit the user's files."
- Inferred, from the hook, `../` link and README findings: a folder-only copy would lose the session-start injection, and a skill copied without its siblings would have broken `../` links. Nothing was run.

### mattpocock/skills

- A written convention keeps shared reference docs in the owning skill ([MP .agents/invocation.md](https://github.com/mattpocock/skills/blob/bbadaa631c/.agents/invocation.md)): "Shared reference docs live inside the skill that owns them; other skills reach that material by calling the Skill tool with it, not by linking across folders."
- `domain-modeling` owns the glossary and ADR formats ([MP skills/engineering/domain-modeling/SKILL.md](https://github.com/mattpocock/skills/blob/bbadaa631c/skills/engineering/domain-modeling/SKILL.md)): "Use the format in [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md)."
- Skills follow the call rule, for example ([MP skills/engineering/grill-with-docs/SKILL.md](https://github.com/mattpocock/skills/blob/bbadaa631c/skills/engineering/grill-with-docs/SKILL.md)): "Call the Skill tool twice, for \"grilling\" and \"domain-modeling\"."
- A user-invoked skill is named for the human to run ([MP to-tickets/SKILL.md](https://github.com/mattpocock/skills/blob/bbadaa631c/skills/engineering/to-tickets/SKILL.md)): "The issue tracker and triage label vocabulary should have been provided to you. If not, tell the user to run `/setup-matt-pocock-skills`."
- An unreleased skill breaks the rule: `chief-of-staff` reads `../retro/SKILL.md`, `../to-spec/SKILL.md` and others by relative path ([mattpocock/skills .changeset/chief-of-staff-shared-wiki-procedures.md, bbadaa631c](https://github.com/mattpocock/skills/blob/bbadaa631c/.changeset/chief-of-staff-shared-wiki-procedures.md)): "reading each skill by relative path so they can stay user-invoked."
- In the source tree `chief-of-staff` sits in `skills/in-progress/` and the skills it reads sit in `skills/engineering/` (tested 2026-11-28: `find skills -type d -name <name>`). Inferred, from that layout: the `../` paths resolve only in a flat install.
- The setup skill seeds the consuming repository's facts ([MP skills/engineering/setup-matt-pocock-skills/SKILL.md](https://github.com/mattpocock/skills/blob/bbadaa631c/skills/engineering/setup-matt-pocock-skills/SKILL.md)): "The contents of `docs/agents/issue-tracker.md`, `docs/agents/domain.md`, and `docs/agents/triage-labels.md` (the last only when `triage` is installed)".
- It edits `CLAUDE.md`, else `AGENTS.md`, else asks, and updates its block in place (same file): "update its contents in-place rather than appending a duplicate." It may also run `gh label create` and `git remote add origin <url>`.
- Seed templates in the setup folder own the `docs/agents/*.md` formats (same file): "write the docs files using the seed templates in this skill folder as a starting point".
- Only the setup skill names `docs/agents/domain.md` (tested 2026-11-28: `grep -rln "docs/agents/domain.md" skills` returned only `skills/engineering/setup-matt-pocock-skills/SKILL.md`).
- CI runs one job, the frontmatter check ([MP .github/workflows/check.yml](https://github.com/mattpocock/skills/blob/bbadaa631c/.github/workflows/check.yml)): "run: npm run check-frontmatter".
- Seeded copies go stale until setup runs again ([MP CHANGELOG.md 1.3.2](https://github.com/mattpocock/skills/blob/bbadaa631c/CHANGELOG.md)): "Re-run `/setup-matt-pocock-skills` to refresh `docs/agents/issue-tracker.md`."
- ADR 0002 rejected committed duplicate skill copies and records that Codex drops symlinks ([MP .agents/adr/0002-ship-as-a-claude-code-plugin.md](https://github.com/mattpocock/skills/blob/bbadaa631c/.agents/adr/0002-ship-as-a-claude-code-plugin.md)): "Codex copies the plugin tree into its cache and **drops symlinks**".
- The README offers plugins and skills.sh ([MP README.md](https://github.com/mattpocock/skills/blob/bbadaa631c/README.md)): "When the installer asks which skills to take, include `setup-matt-pocock-skills`." Gemini installs copy skill folders ([MP .agents/install-block.md](https://github.com/mattpocock/skills/blob/bbadaa631c/.agents/install-block.md)): "`gemini skills install` (copies)".
- The plugin ships only the skill folders listed in `.claude-plugin/plugin.json` ([MP .agents/adr/0002](https://github.com/mattpocock/skills/blob/bbadaa631c/.agents/adr/0002-ship-as-a-claude-code-plugin.md)), so the root `CLAUDE.md`, `.agents/` and `docs/` are not installed.

## How do `google/elephant-goldfish-model` and `open-gsd/gsd-core` handle each item under Constraints?

- `egm-bootstrap` owns the README contract format through its own template and schema ([EGM `skills/egm-bootstrap/SKILL.md`, 46933754e6](https://github.com/google/elephant-goldfish-model/blob/46933754e6/skills/egm-bootstrap/SKILL.md)): "Read [README templates](references/templates.md) before writing".

- Install routes are plugin marketplaces only ([EGM `docs/site/install.md`, 46933754e6](https://github.com/google/elephant-goldfish-model/blob/46933754e6/docs/site/install.md)).
- `egm-bootstrap` writes contracts into the consuming repository ([EGM `skills/egm-bootstrap/SKILL.md`, 46933754e6](https://github.com/google/elephant-goldfish-model/blob/46933754e6/skills/egm-bootstrap/SKILL.md)): "`target_filename`: Contract filename to generate or update (default: `"README.md"`, or e.g. `"EGM.md"` when preserving human-written READMEs)".

## How do `github/spec-kit` and `Fission-AI/OpenSpec` handle each item under Constraints?

### github/spec-kit
