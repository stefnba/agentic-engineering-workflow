# How seven agent-workflow repositories question the user before writing or building

## Answer

Every repository has at least one step that interviews the user before anything is built. They split on three points: how many questions go in one message, whether a question carries the agent's recommended answer, and whether the user approves what gets written. The table shows each repository's main step as of 2026-11-28, read from the default branch.

| Repository | Main questioning step | Questions per message | Options and recommendation | How it ends, and what the user confirms |
| --- | --- | --- | --- | --- |
| `obra/superpowers` | `brainstorming` | One | Open questions until the why is known, then options with the agent's pick | The user approves the written design doc before anything is built |
| `mattpocock/skills` | `grilling`, run by `grill-me`, `grill-with-docs` and `wayfinder` | The whole frontier, numbered | A recommendation on every question; "yes" accepts it | Ends when the frontier is empty and the user confirms a shared understanding; grilling writes nothing, `wayfinder` writes decisions with no review |
| `google/elephant-goldfish-model` | `egm-brainstorm`, then `egm-draft`; `egm-lite` | Gates: one; open turns: no limit stated | Brainstorm: no options; draft: options, never ranked; lite: recommends | A readiness gate before reviewers run; the user confirms the brief after it is written |
| `github/spec-kit` | `/speckit.clarify`; `/speckit.specify` asks too | Clarify: one, at most 5 in all; specify: up to 3 together | Clarify: recommended answer first; specify: options, no pick | Clarify saves each answer into the spec as it lands; no separate review |
| `Fission-AI/OpenSpec` | `openspec-explore` | One; a batch only on request | The preferred option with alternatives | No fixed end; writes only after a yes in a separate message |
| `open-gsd/gsd-core` | `new-project`, `discuss-phase` and its modes, `spec-phase`, `explore`, `new-milestone` | Discuss: four single-question turns; batch, power and spec-phase group them | 2-3 options, recommended one highlighted, mostly through `AskUserQuestion` | "Ready?" gates; discuss writes `CONTEXT.md` with no review; `new-milestone` has the user approve each file |
| `bmad-code-org/BMAD-METHOD` | `bmad-facilitate`, `bmad-forge-idea`, `bmad-brainstorming`, `bmad-architecture`, `bmad-ux` | Coaching: one, never more than two things; Fast: one batch | A recommendation only between named alternatives; forge-idea offers its best answer | Facilitate triages open items and waits for the user's read; forge-idea and ux write with no approval step |

- **Where they agree.** All but `egm-brainstorm` read the project before asking and look facts up rather than ask for them. Most keep the agent's guesses apart from the user's answers: superpowers labels "your call", Spec Kit has an Assumptions section, BMAD tags `[ASSUMPTION: ...]`, gsd-core files delegated choices under "Claude's Discretion", `egm-lite` tags `[⚠️ UNVERIFIED]`. OpenSpec keeps the split only in the conversation. Grilling has no such marking, and issue #1407 reports `wayfinder` writing the agent's own items as the user's decisions.
- **Where they differ.** One question per message (superpowers, clarify, explore, forge-idea, facilitate coaching, gsd-core default) against batches (grilling, specify, gsd-core power and spec-phase, facilitate fast). A recommendation always (clarify, grilling, gsd-core default), never (`egm-brainstorm`, `egm-draft`, specify), or only once a choice can be named (superpowers, facilitate). Superpowers and mattpocock refuse the harness question tool; gsd-core uses `AskUserQuestion` with a plain-text fallback.
- **Unanswered questions.** Clarify lists them as Deferred, gsd-core power mode keeps them as deferred items, and BMAD triages them before finalizing. Superpowers and grilling have no written rule, and grilling issue #1406 reports unanswered questions coming back renumbered.
- **Reported problems.** Three failures recur across repositories: answers to questions taken as approval to write or build, open questions settled silently by the agent, and question tools that exist in only one harness. One-at-a-time against batching is reported as a problem in both directions: superpowers users ask for batches, grilling users ask to go back to one at a time. Spec Kit and OpenSpec mostly fixed theirs; superpowers and mattpocock hold many open ones. EGM has no failure reports.
- **How strong the evidence is.** The skill texts were read in full where cited, and they are current. Three things weaken them. Several steps changed weeks ago and are still being tuned (superpowers v7.0.2, grilling, OpenSpec explore). The default branch is ahead of the release for BMAD (`main` is the v7 alpha; v6.12.4 has separate PRD and brief skills) and for EGM (`egm-lite` is in no release). Issue bodies were read only in part, many reports are filed by AI agents, and some failures reproduce in only a share of runs.

## In `obra/superpowers` and `mattpocock/skills`, which skills question the user, and how does each cover the points listed under Constraints?

This section also holds the `wayfinder` findings from the sub-question added after confirmation.

### obra/superpowers

- `brainstorming` is the only skill that questions the user before building: "You MUST use this before any creative work" ([brainstorming/SKILL.md, main 22f0b46](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)). `writing-plans` starts from an existing spec and does not interview (tested 2026-11-28: grep of [writing-plans/SKILL.md, main](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md) for `ask|question` found no such instruction).
- It reads what the user pointed at and the code it touches before asking: "Never ask what the project or their context already answers, or reopen what they've already decided." ([brainstorming/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md))
- It asks only what changes the build, one question at a time: "Ask a question only when the answer would change what gets built and neither the request nor the project answers it. Otherwise, state your call and your reason as a proposal they can correct ... Ask one at a time." (same source)
- Until the why is known it asks open questions with no example answers. After that it sketches choices "with what it trades off and which you'd pick". The Red Flags table says "Options steer." (same source)
- The approaches go in a message of their own, two or three with trade-offs: "Recommend one and say why, then ask which way they want to go". (same source)
- Playback keeps the user's words apart from the agent's: "Only what they said goes in as theirs. Anything you filled in goes in as your proposal, with your reason." In the design, any choice the agent made goes in "as your call, never as something they agreed to". (same source)
- After writing, a fresh subagent reads the doc as a builder ([builder-check-prompt.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/builder-check-prompt.md)). The agent answers what the doc already covers, settles minor points as marked calls, and brings the rest "in one message, most important first". "That's the only round of questions the check produces." ([brainstorming/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md))
- The design doc goes to `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`, committed. A hard gate follows: "Nothing gets built until your human partner approves the design doc". The exceptions are a user who opted out and an agreed spike. (same source)
- The skill sets no cap on questions and no explicit end of the conversation. It moves on "Once you understand what they want". (same source)
- The file's last commit is `22f0b46`, Release v7.0.2, 2026-11-03 (tested 2026-11-28: `gh api --method GET "repos/obra/superpowers/commits?path=skills/brainstorming/SKILL.md"`). v7.0.0 rebuilt the skill on 2026-10-10 ([release notes](https://github.com/obra/superpowers/releases/tag/v7.0.0)).
- v7.0.2 cut filler questions "from 41 with 7.0.1 to 23" in blind-graded test conversations; the release notes say it "further tunes brainstorming's questions" ([v7.0.2 release notes, 2026-11-03](https://github.com/obra/superpowers/releases/tag/v7.0.2)).
- Inferred: unanswered questions are not tracked as a list. Unasked points become proposals the user can correct, and the builder check gets one round only. This rests on the one-at-a-time, proposal and builder-check findings.

### mattpocock/skills

- `grilling` is the questioning primitive. `grill-me` only calls it ([grill-me/SKILL.md, main](https://github.com/mattpocock/skills/blob/main/skills/productivity/grill-me/SKILL.md)). `grill-with-docs` calls it together with `domain-modeling` ([grill-with-docs/SKILL.md, main](https://github.com/mattpocock/skills/blob/main/skills/engineering/grill-with-docs/SKILL.md)). `improve-codebase-architecture`, `wayfinder` and the in-progress `loop-me` call it too (tested 2026-11-28: grep of every `skills/**/*.md` on `main` for `grill|interview|recommended answer`).
- It asks in rounds: "Ask the whole frontier in one round: number each question and give your recommended answer. Then wait for the user's answers before the next round." Order follows dependency: a question that depends on one still open "belongs to a _later_ round" ([grilling/SKILL.md, main 7739eae](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md)).
- Each question has a fixed format with its choices and a `➡️` recommended answer. "Word each question so "yes" accepts your recommended answer." (same source) That wording was added on 2026-10-07 (#1193) (tested 2026-11-28: commit history of `skills/productivity/grilling/SKILL.md`).
- Facts are the agent's to find, through "a sub-agent with a fresh context window"; only the questions downstream of a lookup wait. "The _decisions_ are the user's: put each to them and wait." ([grilling/SKILL.md](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md))
- It ends "when the frontier is empty: every branch of the design tree visited, nothing left silently assumed. Do not act on it until the user confirms you have reached a shared understanding." (same source)
- There is no cap on questions, by design. The user's way out is to say "wrap up, summarise, and move on" ([.out-of-scope/question-limits.md, main](https://github.com/mattpocock/skills/blob/main/.out-of-scope/question-limits.md)).
- Questions go as plain chat text. Native question tools are out of scope because "Structured pickers push the model towards multiple-choice questions with pre-baked answers" ([.out-of-scope/native-question-tool.md, main](https://github.com/mattpocock/skills/blob/main/.out-of-scope/native-question-tool.md)). The same note still says grilling asks "one branch of the decision tree at a time", which the skill no longer does.
- Grilling writes nothing. Under `grill-with-docs`, `domain-modeling` updates `GLOSSARY.md` "right there" when a term is resolved, and offers an ADR only for a decision that is hard to reverse, surprising and a real trade-off ([domain-modeling/SKILL.md, main](https://github.com/mattpocock/skills/blob/main/skills/engineering/domain-modeling/SKILL.md)).
- Commit `a4b2009` replaced one question at a time with frontier rounds. It was authored on 2026-07-16 and committed to the branch on 2026-07-31 (tested 2026-11-28: `gh api --method GET repos/mattpocock/skills/commits/a4b2009`, author and committer dates).
- `to-questionnaire` asks the user only who the recipient is and what they need back, then writes a questionnaire for someone else to fill in ([to-questionnaire/SKILL.md, main](https://github.com/mattpocock/skills/blob/main/skills/productivity/to-questionnaire/SKILL.md)).
- Inferred: grilling keeps answers apart from assumptions only through its end condition and the facts-or-decisions split. Its file has no playback, no marking of guesses and no list of open points. This rests on the grilling findings above.

### wayfinder (mattpocock/skills)

- `wayfinder` asks nothing itself. It grills once to name the destination, then "**breadth-first**" to map the frontier, then again for each grilling ticket ([wayfinder/SKILL.md, main 7739eae](https://github.com/mattpocock/skills/blob/main/skills/engineering/wayfinder/SKILL.md)). The docs page sets it apart from `grill-with-docs` as the multi-session planner ([docs/engineering/wayfinder.md, main](https://github.com/mattpocock/skills/blob/main/docs/engineering/wayfinder.md)).
- It records on the issue tracker. A resolved ticket gets "a **resolution comment**", is closed, and gets a pointer under the map's "Decisions so far". A precise open question becomes a ticket; a vague one goes under "Not yet specified"; ruled-out work goes under "Out of scope" ([wayfinder/SKILL.md](https://github.com/mattpocock/skills/blob/main/skills/engineering/wayfinder/SKILL.md)).
- The agent picks the next ticket: "you pick the next decision, not the user." It resolves at most one ticket per session, except research tickets. (same source)
- Inferred: no step has the user review a resolution comment or a Decisions-so-far line before it is written, and nothing marks the agent's own inferences. This rests on the recording findings; issue #1407 (below) reports the same gap.

## In `google/elephant-goldfish-model` and `github/spec-kit`, which skills or commands question the user, and how does each cover the points listed under Constraints?

This section also holds the EGM findings from the sub-question added after confirmation.

### google/elephant-goldfish-model

- `egm-brainstorm` is the main interview and is user-invoked only. It asks "open-ended plain-text questions across multiple chat turns", and is "STRICTLY FORBIDDEN from using structured question tools (`ask_question`) or supplying pre-canned multiple-choice candidate answers" ([skills/egm-brainstorm/SKILL.md, main 2026-11-28](https://github.com/google/elephant-goldfish-model/blob/main/skills/egm-brainstorm/SKILL.md)).
- Its one-question rule binds gates only: "All interactive gates ... MUST contain strictly one question (`len(questions) == 1`)", with options "without `(Recommended)` prefixes" ([egm-brainstorm SKILL.md, main 2026-11-21](https://github.com/google/elephant-goldfish-model/blob/main/skills/egm-brainstorm/SKILL.md)). Step 1 lists six example questions and sets no per-message limit. (same source)
- The stricter rule, "You are strictly forbidden from asking more than one question in a single response", sits under a heading scoped to `egm-draft` only ([resources/execution_instructions.md, main 2026-11-24](https://github.com/google/elephant-goldfish-model/blob/main/resources/execution_instructions.md)). `egm-brainstorm` does not reference that file (tested 2026-11-28: `grep -n "execution_instructions"` on the skill returned no match).
- The design doc and tests count no questions. The test scenario checks only for open inquiry and no menus ([test_scenarios.yaml, main 2026-11-05](https://github.com/google/elephant-goldfish-model/blob/main/skills/egm-brainstorm/test_scenarios.yaml); [docs/designs/brainstorm.md, main](https://github.com/google/elephant-goldfish-model/blob/main/docs/designs/brainstorm.md)).
- Inferred: an agent following `egm-brainstorm` may put several open questions in one message without breaking a written rule. This rests on the gate-only rule, the draft-only scope of the strict rule and the missing reference.
- Before asking, Step 1 only checks for a concept and resolves the author's name. The skill does not tell the agent to read code; the Goldfish reviewers read it later ([egm-brainstorm SKILL.md, main 2026-11-28](https://github.com/google/elephant-goldfish-model/blob/main/skills/egm-brainstorm/SKILL.md)).
- It ends with a 2-3 sentence hypothesis and a single-select readiness gate, and "MUST NOT spawn subagents until the user explicitly confirms readiness". Reviewers then write `concepts_brief.md`, whose template has no section for open questions or assumptions. (same source)
- The agent brings back "2-3 key objections or open risks" and repeats until "the user is satisfied". Step 4 asks the user to "confirm their alignment" with the brief, which Step 2 has already written ([egm-brainstorm SKILL.md, main](https://github.com/google/elephant-goldfish-model/blob/main/skills/egm-brainstorm/SKILL.md)).
- `egm-draft` reads the brief or another context file first. For architecture choices it shows up to three options: "Do not rank the options, mark a default, or pick one. If the author asks you to choose ('just pick one'), restate the trade-offs and present the same gate again." Each section needs an approve-or-revise gate ([skills/egm-draft/SKILL.md, main 2026-11-28](https://github.com/google/elephant-goldfish-model/blob/main/skills/egm-draft/SKILL.md)).
- At finalization `egm-draft` lists each contradiction between brief and draft: "If a contradiction is open, stop and wait for the user." (same source)
- `egm-lite` reads target files, callers, tests and docs first. It flags an unchecked claim `[⚠️ UNVERIFIED]`, and the user either verifies it or defers it with `[⏳ ACK]`. It does state a "recommended option". It ends when the user types `checklist` ([skills/egm-lite/SKILL.md, main 2026-11-28](https://github.com/google/elephant-goldfish-model/blob/main/skills/egm-lite/SKILL.md)).
- `egm-lite` was created on 2026-11-18, and brainstorm and draft were last changed on 2026-11-21 (#418). Both dates fall after v0.1.1 (2026-11-06), so `egm-lite` is in no release (tested 2026-11-28: `gh api --method GET "repos/google/elephant-goldfish-model/commits?path=skills/<skill>/SKILL.md&sha=main"`).

### github/spec-kit

- `/speckit.clarify` is the dedicated interview, run before planning. A user who skips it gets a warning that "downstream rework risk increases" ([templates/commands/clarify.md, main 2026-11-28](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md)).
- It reads the constitution and the spec, then marks each category of a fixed taxonomy "Clear / Partial / Missing". It queues at most 5 questions, the "top 5 by (Impact * Uncertainty)". (same source)
- "Present EXACTLY ONE question at a time", and "Never reveal future queued questions in advance." An answer is 2-5 options or a short phrase of at most 5 words. (same source)
- Multiple-choice questions lead with "`**Recommended:** Option [X] - <reasoning>`"; short-answer questions carry a "`**Suggested:**`" answer. "yes", "recommended" or "suggested" accepts it. (same source)
- It stops when the critical ambiguities are resolved, when the user says "done", or at 5 questions. (same source)
- After each answer it appends "`- Q: <question> → A: <final answer>`" under `## Clarifications`, edits the matching section and saves. The answer is the only confirmation. (same source)
- Points left at the cap are flagged "under Deferred with rationale". A coverage table reports Resolved, Deferred, Clear and Outstanding. (same source)
- `/speckit.specify` writes first: "Make informed guesses based on context and industry standards", with the guesses in an Assumptions section. It leaves at most 3 `[NEEDS CLARIFICATION: ...]` markers, then will "Present all questions together", each with a table of suggested answers and no recommended one ([templates/commands/specify.md, main 2026-11-28](https://github.com/github/spec-kit/blob/main/templates/commands/specify.md); [templates/spec-template.md](https://github.com/github/spec-kit/blob/main/templates/spec-template.md)).
- `/speckit.checklist` asks up to three questions about the checklist's scope, plus at most two follow-ups, with no recommendation ([templates/commands/checklist.md, main](https://github.com/github/spec-kit/blob/main/templates/commands/checklist.md)). `/speckit.plan` turns its unknowns into research tasks and asks nothing ([templates/commands/plan.md, main](https://github.com/github/spec-kit/blob/main/templates/commands/plan.md)).
- The lean preset's `specify` asks nothing (tested 2026-11-28: `gh api --method GET "repos/github/spec-kit/contents/presets/lean/commands/speckit.specify.md?ref=main" -H "Accept: application/vnd.github.raw" | grep -n -iE 'clarif|question|assum'` returned no lines).
- The last behaviour change to clarify was #4507 on 2026-09-15, so v1.4.5 matches `main` (tested 2026-11-28: `gh api --method GET "repos/github/spec-kit/commits?path=templates/commands/clarify.md&sha=main&per_page=8"`).
- Inferred: specify and clarify contradict each other on batching and on recommending. This rests on the two templates' findings.

## In `Fission-AI/OpenSpec` and `open-gsd/gsd-core`, which skills, commands or agents question the user, and how does each cover the points listed under Constraints?

This section also holds the gsd-core findings from the sub-question added after confirmation.

### Fission-AI/OpenSpec

- `openspec-explore` (`/opsx:explore`) is the one real questioning step. Its text is generated from `explore.ts`, which says "This is a stance, not a workflow", and it interviews only when the user is planning a change ([src/core/templates/workflows/explore.ts, main 2026-11-28](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/explore.ts)).
- "Ask one focused question at a time, and briefly explain why it matters and which decision it unlocks. Batch questions only if the user asks for a batch". It resolves "the next blocking decision before its dependent details". (same source)
- It states "your preferred option and why it fits the user's goals, with alternatives and their tradeoffs when useful", with no fixed question format. (same source)
- The same file keeps older lines that pull the other way: "Surface multiple interesting directions" and "Recommend a path (if asked)". (same source)
- Before a factual question it inspects "relevant OpenSpec artifacts, source, tests, docs, and configuration. Do not ask the user to repeat facts you can verify." It runs `openspec list` and reads relevant specs in full. (same source)
- "Track decisions in the conversation, not in files. Separate confirmed decisions from proposed defaults and unresolved questions. Silence is not acceptance." (same source)
- The user may defer a decision, and an optional closing summary lists "**Open questions**". "Stop asking when the user has enough clarity." "There's no required ending." (same source)
- "Answering design or clarifying questions is never consent to write." Before writing it names the files and waits for a yes "in a separate message". An explicit request to capture the exploration counts as that yes. (same source)
- `openspec-propose` asks only about ambiguity that "would materially affect scope, externally observable behavior, compatibility, or acceptance criteria", and records minor details as assumptions. It writes every artifact, then hands the plan over for review ([propose.ts, main 2026-11-28](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/propose.ts)). `ff-change` prefers "making reasonable decisions to keep momentum" ([ff-change.ts, main 2026-11-28](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/ff-change.ts)).
- A design's "Open Questions" section may hold only questions that can wait: "If a question would change the specs, the chosen approach, or the task breakdown, resolve it now - ask the user instead of guessing." ([schemas/spec-driven/schema.yaml, main](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml))
- The questioning rules date from #1017 on 2026-09-02, and the write confirmation from #1832 on 2026-09-16. The newest commit to `explore.ts` is older than v2.2.0 (tested 2026-11-28: `gh api --method GET "repos/Fission-AI/OpenSpec/commits?sha=main&path=src/core/templates/workflows/explore.ts&per_page=12"`).
- The changelog records that write confirmation was added because "an agent could treat a design discussion as a go-ahead" (#1716) ([CHANGELOG.md, main](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)).

### open-gsd/gsd-core: new-project, spec-phase, explore and new-milestone

- `/gsd:new-project` asks its first question as free text, then probes with `AskUserQuestion`: "options that probe what they mentioned" ([workflows/new-project.md, next 2026-11-28](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/new-project.md)).
- The questioning guide asks for 2-4 options and bans leading ones. "When the user wants to explain freely, STOP using AskUserQuestion." It loops until the user picks "Create PROJECT.md" ([references/questioning.md, next](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/references/questioning.md)). In auto mode new-project skips questioning entirely ([new-project.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/new-project.md)).
- `/gsd:spec-phase` runs "**Max 6 rounds.** Each round: 2–3 questions max", each round from a set perspective. It scouts the code first and keeps the result internal ([workflows/spec-phase.md, next](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/spec-phase.md)).
- spec-phase ends on a score, "ambiguity ≤ 0.20 AND all dimensions ≥ their minimums", and the user then chooses to write `SPEC.md`. After six rounds without passing, the user may write it anyway with gaps flagged in an "Ambiguity Report". (same source)
- `/gsd:explore` asks "**one question at a time** (never a list of questions)" over 2-5 exchanges. It writes only what the user selects, and an unresolved claim is written "**as unresolved**" ([workflows/explore.md, next](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/explore.md)).
- `/gsd:new-milestone` reads `PROJECT.md`, `MILESTONES.md` and `STATE.md`, asks "What do you want to build next?" as free text, then probes with `AskUserQuestion` ([workflows/new-milestone.md, next](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/new-milestone.md)).
- new-milestone has three approval loops. "Before writing any files, present a summary of what was gathered and ask for confirmation", looping until "Looks good". The full requirements list and the roadmap each loop until approved, and each is committed after approval. (same source)
- `list-phase-assumptions` lists the agent's assumptions as "Fairly confident", "Assuming" or "Unclear", asks one open "What do you think?", and writes no file. Its usage text points to `/gsd:discuss-phase <phase-number> --assumptions` ([workflows/list-phase-assumptions.md, next](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/list-phase-assumptions.md)).

### open-gsd/gsd-core: discuss-phase and its modes

- discuss-phase aims at "decisions clear enough that downstream agents can act without asking the user again" ([commands/gsd/discuss-phase.md, next](https://github.com/open-gsd/gsd-core/blob/next/commands/gsd/discuss-phase.md)).
- It reads `PROJECT.md`, `REQUIREMENTS.md`, `STATE.md`, recent `CONTEXT.md` files and codebase maps first, and marks gray areas already decided as pre-answered. With a phase `SPEC.md`, it asks only how to build ([workflows/discuss-phase.md, next](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/discuss-phase.md)).
- The user picks the areas in one multi-select with no skip option. Then: "Default flow is 4 single-question turns, then check whether to continue."
